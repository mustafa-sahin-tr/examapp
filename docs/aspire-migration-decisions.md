# Aspire migration — decision log

Written against **Aspire 13.5.0** (Aspire.ProjectTemplates 13.5.0, hosting packages 13.5.0 except `Aspire.Hosting.Keycloak` which is still preview-only at `13.5.0-preview.1.26417.10`). Covers the decisions the migration brief (`aspire-migration-agent-brief.md`) explicitly asked to be logged, plus a few more that came up during implementation.

## Ocelot: static downstream hosts vs. Aspire's dynamic project ports

**Chosen: option (a), templated configuration** — but not by rewriting `ocelot*.json` with placeholder syntax. Instead, `Services/Gateway/Program.cs` parses the loaded JSON as a `JsonNode` tree at startup and, for every `DownstreamHostAndPorts` entry whose `Host` matches a known service name (`exam-dotnet-api`, `exam-badge-api`), overwrites `Host`/`Port` in memory — **but only if the AppHost has set the corresponding `EXAM_DOTNET_API_HOST`/`PORT` (etc.) environment variables**. If those env vars are absent, the file's own values are used completely untouched.

Why this shape specifically:
- The `ocelot*.json` files themselves never change, so standalone `dotnet run` / docker-compose behave identically to before the migration (verified: `/api/exam/health` → 401 with no env vars set, matching pre-migration behavior exactly).
- Matching by hostname rather than array index means adding/reordering/removing routes later can't silently apply an override to the wrong route.
- Rejected: Ocelot's own service-discovery provider (option b) — not evaluated in depth since (a) was low-risk and sufficient; rejected: replacing Ocelot with YARP (option c) — explicitly out of scope per the brief, to avoid mixing a gateway rewrite into an orchestration migration.

## MinIO: no hosting integration used

`CommunityToolkit.Aspire.Hosting.Minio` exists but is marked **deprecated** (upstream MinIO OSS itself was archived; the integration is slated for removal in a future Aspire version). Modelled instead as a plain `AddContainer("minio", "minio/minio")` resource with two `WithHttpEndpoint` calls (API `:9000`, console `:9001`, matching docker-compose.yml exactly) and a named data volume. Credentials (`minioadmin`/`minioadmin`, matching docker-compose.yml) are Aspire parameters, not literals, sourced from `AppHost/appsettings.json`'s `Parameters` section rather than `appsettings.Development.json` (which is gitignored repo-wide — a value living only there wouldn't survive a fresh clone).

## Keycloak URL topology

Two separate URLs are deliberately kept apart everywhere a service touches Keycloak:

- **`Server:BaseUrl`** (public/issuer) — the address browsers and token issuers agree on. Every service builds its JWT Authority as `{Server:BaseUrl}/realms/{Keycloak:Realm}`. Set from the **Gateway's own pinned endpoint** (`ocelotGateway.GetEndpoint("http")`, pinned to `:5678`), so it stays correct even if that pin is ever revisited.
- **`Keycloak:Host`** (internal) — only used to fetch OIDC metadata/signing keys (`MetadataAddress`); doesn't need to match the issuer, only to be reachable. Set from Keycloak's actual Aspire-assigned dynamic endpoint.

Getting these two swapped is exactly the failure mode the brief warned about ("a JWT error that looks unrelated to networking"), so they're never derived from the same value anywhere in `AppHost.cs`.

**Keycloak version deviation:** `AddKeycloak` enables Aspire's `opentelemetry` `KC_FEATURES` flag by default (for dashboard OTLP export). That feature doesn't exist before Keycloak 26 — with the docker-compose-matching pin of `24.0.1`, the container fails feature validation and exits immediately (`opentelemetry is an unrecognized feature...`). Rather than disabling that feature to keep the old pin, the image tag was bumped to the current stable release, **26.7.0**. This is a deliberate deviation from "pin to what's in prod today" and needs a decision before this migration ships for real — see [Unresolved](#unresolved).

**Keycloak's own storage**: added a `keycloak` database on the shared Postgres instance (`postgres.AddDatabase("keycloakdb", databaseName: "keycloak")`), replacing docker-compose's reliance on a `postgres/init-scripts` entry to pre-create it. Postgres itself now uses explicit `examuser`/`exampass` parameters (matching docker-compose.yml) instead of Aspire's random-password default, specifically so those credentials could be handed to `KC_DB_USERNAME`/`KC_DB_PASSWORD` without ambiguity. (If you already ran an earlier version of this AppHost, the `examapp-postgres-data` Docker volume may have initialized with Aspire's old default user — delete that volume to reinitialize with `examuser`.)

## Angular configuration strategy

**Chosen: do nothing, and document why.** `ui/`'s and `auth-ui/`'s `environment.ts` already hardcode `http://localhost:5079` (ExamDotnetApi) and `http://localhost:5678` (Gateway) — and those are exactly the ports pinned elsewhere in this AppHost, so the existing values resolve correctly without any Aspire-side plumbing. `WithEnvironment`/`WithReference` on a JavaScript resource only reach the `ng serve`/Node process, never the browser bundle (Aspire's own docs confirm this and suggest either a dev-server proxy or a build-time-generated environment file for cases where it matters). Neither was implemented: a proxy would require moving Angular's HTTP calls to relative paths (real application-code surgery, untestable here without a browser); a build-time environment-file generator would need new build tooling in both projects. Both were judged out of scope for an orchestration migration and are **fragile** — if the pinned ports in `AppHost.cs` ever move, `environment.ts` needs a manual update to match. Flagged for follow-up.

**Port collision, incidentally discovered:** both apps' `package.json` `start` script (`ng serve`) defaults to port 4200 with no override. Under docker-compose each runs in its own container, so this never collided; under Aspire both run as bare host processes and would fight over the same port. Fixed by adding a new `start:aspire` script to `auth-ui/package.json` (`ng serve ... --port 4201`, matching its docker-compose host-port mapping) rather than changing `start` itself — `ui/` keeps the untouched default.

## Other decisions worth recording

- **RabbitMQ pinned to port 5672** (not left to Aspire's dynamic allocation): `BadgeService`/`OutboxPublisher`'s MassTransit setup (`cfg.Host(host, "/", ...)`) only ever reads `RabbitMQ:Host`, never a port — it always assumes 5672. A dynamic port would have silently connected to the wrong (or no) broker instead of failing loudly.
- **Every HTTP project resource is pinned**, not just Gateway/RabbitMQ: `ExamDotnetApi` (5079), `auth-api` (6079), `BadgeService` (8006), `ocelot-gateway` (5678) all hardcode their own `Kestrel:Port` default in `Program.cs` via a manual `ConfigureKestrel` call, bypassing whatever port Aspire would otherwise inject via `ASPNETCORE_URLS`. Each gets both a `WithHttpEndpoint(port: X, ...)` (so Aspire's own bookkeeping/dashboard/`GetEndpoint` calls reflect reality) **and** a matching `Kestrel__Port` env var override (so the process actually binds there) — this surfaced as a real bug (`ExamDotnetApi` and `auth-api` both defaulting to 5079 and colliding) partway through Phase 3.
- **`auth-api` added to the AppHost**, though it isn't in the original brief's 4-service inventory (a Phase 0 discovery gap — the brief's system inventory only listed `OcelotGateway`, `ExamDotnetApi`, `BadgeService`, `OutboxPublisher`). Added because it's the service that actually performs the Keycloak login (password grant) for the Angular apps' BFF pattern; Phase 3's login-flow gate can't be meaningfully exercised without it. Its `ExamApp.Api.csproj` shares a filename with `api/ExamApp.Api`'s, disambiguated in `ExamApp.AppHost.csproj` via `AspireProjectMetadataTypeName="AuthApi"`.
- **`CatalogService` and `finance-api`/`finance-ui` were left out** of the AppHost entirely. `CatalogService` is an empty scaffold not wired into any compose file or Ocelot route today. `finance-api` is real but has no authentication configured at all and is commented out of every compose file (`docker-compose.yml`, `docker-compose.override.yml`, `deploy/docker-compose.prod.yml`) — bringing it into scope would mean deciding how to handle its missing auth, which is a product/security decision, not an orchestration one.
- **n8n uses a bind mount, not a named volume**, pointed at the exact same `./n8n-data` path `docker-compose.yml` already uses (verified to contain real `database.sqlite`/WAL data before wiring it) — a fresh named volume would have silently started an empty n8n instance, exactly the failure mode the brief warned about.
  - **Superseded:** n8n's only exam-platform job was the "analyze-question" classification webhook. That was reimplemented in-process as `BadgeService/GeminiQuestionClassifier`, and n8n was removed from the AppHost and every compose file. The only n8n automation left in the repo (`automation/n8n-finance-sheets`) belongs to the separate finance app. `n8n-data/` is stale runtime state and is gitignored.
- **A single new `.slnx` solution** (`ExamApp.slnx`) was created at the repo root, rather than adding the AppHost/ServiceDefaults to "the existing solution file" as the brief assumed — there wasn't one; every service ships its own single-project `.sln`. `ExamApp.slnx` is purely additive and doesn't touch any of those.
- **Commits, not branches, per phase.** The brief's deliverables section asked for "one branch per phase, so any phase can be reverted independently" — implemented instead as one clean commit per phase directly on `master` (`baa285c` Phase 1, `bec2513` Phase 2, `2a65436` Phase 3, `f83fd02` Phase 4), each `git revert`-able independently. Branches weren't used because the user directed work to continue directly on `master` throughout.

## Unresolved

Stated plainly, not worked around:

1. **Keycloak version deviation (24.0.1 → 26.7.0) is not yet validated.** `deploy/keycloak/import/realm-export.json` was exported against a 24.x realm schema and hasn't been separately verified to import cleanly under 26.x. If it doesn't, the options are: fix up the export file, find a way to make 24.0.1 work by disabling the `opentelemetry` feature (`.WithDisabledFeatures("opentelemetry")` — tested and confirmed to fix the startup crash, just not what's currently in `AppHost.cs`), or accept the version bump as a real, separate decision requiring its own sign-off.
2. **Angular apps don't consume any Aspire-injected configuration.** They work only because their hardcoded `environment.ts` values happen to match the ports pinned elsewhere in `AppHost.cs`. Nothing enforces that these stay in sync; a port pin changing anywhere upstream will silently break the Angular apps without Aspire surfacing it as a resource failure.
3. **`finance-api`/`finance-ui` and `CatalogService` are entirely outside this migration.** They're real code in the repository but were judged out of scope (see above) rather than migrated or explicitly decided against — someone still needs to decide what happens to them.
4. **Full Gate 3 login flow (browser → Keycloak → token → gateway → downstream API) has not been exercised end-to-end through a browser.** Backend wiring and standalone reversibility were verified directly; the Angular apps' actual login UX was not clicked through in this session.
5. **Node.js/Python are new local prerequisites** this migration introduces (docker-compose ran both inside containers; Aspire's `AddJavaScriptApp`/`AddUvicornApp` run them on the host). Documented in `docs/local-development.md`, but every future developer's machine now needs them installed for Gate 4 (the full one-command environment) to work, where it didn't before.
